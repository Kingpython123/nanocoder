# nanocoder 产品化头脑风暴

> 目标：把 nanocoder 从“跑分的评测器”变成**别人真的会装、会用的产品**。
> 参考的开源项目（2026-10 的热度来自聚合站，星数仅供参考）：OpenCode、OpenAI Codex CLI、OpenHands、Cline、Aider、SWE-agent、PR-Agent、Open-Inspect（background-agents）、Orbi，以及 DeepSeek dsh-superagent（见 `doc/dsh-superagent-学习笔记.md`）。
> 下面关于各项目功能的描述来自我对这些项目的了解和搜索摘要，没有逐个读源码核实，借鉴前请回仓库确认。

## 1. 先看清楚：热门项目各自卖的是什么

| 项目 | 形态 | 用户为什么用它（核心卖点） | 我们能借的 |
|---|---|---|---|
| OpenCode | 终端 TUI + 客户端/服务端分离 | 模型随便换、本地优先、体验好 | 服务端/客户端分离：一个 agent 内核，多个前端 |
| Codex CLI | 终端 CLI | 系统级沙箱 + 审批模式（只读 / 自动编辑 / 全自动）、`AGENTS.md` | 分级权限模式；仓库级说明文件 |
| Cline | VS Code 插件 | Plan / Act 两种模式、每步可审批、**检查点可回滚** | 计划先给人看；检查点与撤销 |
| Aider | 终端 + git | **repo map**（tree-sitter 提取符号做仓库地图）、每次改动自动 commit、编辑格式基准 | 仓库地图；git 即撤销 |
| OpenHands | Web UI + Docker runtime | 完整的可视化 agent 工作台、GitHub Resolver（给 issue 打标签就修） | 事件流架构；打标签触发 |
| SWE-agent | 研究 / CLI | ACI（为 agent 设计的接口） | 我们已经在用它的思路 |
| PR-Agent | GitHub App / Action | `/review`、`/describe`、`/improve` 命令，**装上就能用** | 最容易落地的切入点 |
| Open-Inspect | 后台 agent 系统 | 从 Slack / Linear / GitHub / Webhook 发起，后台跑，快照环境 | 多入口；环境快照秒级启动 |
| Orbi | 自托管“无人工厂” | issue 打标签 → 独立审查的 PR → 合并 → 发版 | 写代码和审查分离 |
| dsh-superagent | 守着仓库的主动 agent | 授权、少打扰人、可靠交付 | 工单模型、Outbox、observe 模式 |

**结论**：终端 / IDE 交互式 agent 这条赛道太挤（OpenCode、Codex、Cline 都是大团队），学生项目没法赢。**后台型、事件驱动、自托管**的“仓库助手”赛道更合适：
- 和 nanocoder 现有的能力（无人值守、沙箱、评测）天然匹配；
- 产品边界清晰，能做成 GitHub App / Action，**别人装上就能用**；
- 面试时能讲完整链路：触发 → 授权 → 执行 → 交付 → 评测 → 运维。

## 2. 产品定位（建议）

> **nanocoder：自托管的仓库 AI 队友。** 在 GitHub 上 @ 它或给 issue 打标签，它在隔离沙箱里修 bug、修 CI、审 PR，交付一个经过验证、写清楚证据的 PR；支持国产模型和私有部署。

差异化（和 OpenHands / PR-Agent 比）：
1. **证据驱动交付**：每个 PR 附“验证报告”——跑了哪些测试、结果、自评置信度、风险，且报告内容和执行记录自动核对过（第一轮的 B1）。不是“我修好了”，是“这是证据”。
2. **自带回归评测**：你的仓库可以导出自己的历史 bug 做成私有评测集，换模型、改 prompt 之前先跑一遍（这是别家很少有的，也是你项目最强的底子）。
3. **国内可用**：OpenAI 兼容接口，DeepSeek / Qwen / Kimi / 中转站开箱即用；可选飞书 / 企业微信通知；成本按人民币统计。
4. **少打扰人**：借 dsh 的沟通规范，确认一次、完成一次，中间安静。

## 3. 分阶段路线（每一阶段都能单独发布）

| 版本 | 入口 | 做什么 | 为什么这个顺序 |
|---|---|---|---|
| **v0.1 PR 审查** | GitHub Action，PR 上评论 `/nano review` | 读 diff + 相关上下文，给出行内评论；可选 `/nano fix` 把建议直接改成提交 | 只读、风险最低，装上就有价值，最快拿到真实用户反馈 |
| **v0.2 CI 修复** | CI 失败时自动或评论 `/nano fix-ci` | 拉取失败日志 → 在沙箱复现 → 修 → 推到 PR 分支 | 有天然的验收标准（CI 变绿），最适合 agent；和 nanocoder 的“先复现再修”一致 |
| **v0.3 Issue → PR** | issue 打 `nano` 标签或 @ 机器人 | 完整的 nanocoder 流程，开 PR 并附验证报告；PR 评论触发再改 | 核心能力，难度最高，放在有了前两步的基础设施之后 |
| **v0.4 Web 控制台** | 浏览器 | 工单列表、实时 trace 回放、成本看板、一键重试/停止 | 运维和演示都需要 |
| **v0.5 私有评测** | CLI | 从仓库 git 历史自动挖“带测试的修复提交”，生成私有评测集，换模型前自动跑 | 差异化卖点 |

部署形态：先做 **GitHub Action**（用户零运维，跑在 GitHub 的 runner 上，最容易推广）；再做 **自托管服务**（Docker Compose：webhook 服务 + 任务队列 + 沙箱 worker + 控制台），给私有仓库和内网用。

## 4. 功能点头脑风暴（按模块）

### 4.1 触发与入口
- **斜杠命令**（PR-Agent）：`/nano review`、`/nano fix`、`/nano explain`、`/nano test`（给改动补测试）。命令解析是确定性代码，不交给模型。
- **标签触发**（OpenHands Resolver、Orbi）：issue 打 `nano` 标签即开工；去掉标签即停止。
- **多入口统一成工单**（Open-Inspect、dsh）：GitHub、飞书、Webhook、CLI 都转成同一个 Ticket，内核不关心来源。
- **权限**（dsh Gate）：只有仓库 collaborator 或白名单用户能触发写操作；外部贡献者的 PR 只能触发只读审查（防止有人用 issue 内容做 prompt 注入去改代码）。

### 4.2 理解代码库
- **Repo map**（Aider）：用 tree-sitter 抽取所有文件的类、函数签名，按与 issue 的相关度排序后塞进上下文前部。可做消融：有/无 repo map 的定位准确率和步数。
- **`AGENTS.md` / 仓库说明**（Codex、dsh）：读取仓库根目录的 agent 说明（怎么跑测试、代码风格、禁区目录）。没有的话，首次运行时 agent 自动生成一份草稿 PR 让维护者确认——这本身就是个好功能。
- **自动探测测试命令**：读 CI 配置（`.github/workflows`、`tox.ini`、`package.json`）推断怎么装依赖、怎么跑测试，缓存下来。

### 4.3 执行环境
- **环境快照与预热池**（Open-Inspect）：第一次为仓库构建好依赖镜像，之后每个任务从快照秒级启动；常驻 N 个预热容器。指标：任务冷启动时间。
- **分级权限模式**（Codex CLI）：`read-only`（审查）/ `workspace-write`（只改工作区、禁网）/ `full`（允许装依赖时联网，只在白名单域名）。
- **长命令转后台**（dsh）：见学习笔记 E1。
- **资源与成本护栏**：每任务 token / 人民币上限、每仓库每日上限，超限自动停并在工单里说明。

### 4.4 修改与安全网
- **检查点与回滚**（Cline）：每次 edit 前打 git 检查点；agent 可以 `rollback` 到某个检查点；人也可以在控制台一键回退到任意一步。
- **每步自动 commit**（Aider）：工作分支上的提交历史就是 agent 的思路，PR 合并时 squash。
- **改公共接口先报调用点**（学习笔记 C2）。
- **代码层强制**：禁改测试（可配）、危险命令黑名单、禁止改 `.github/workflows`（防止 agent 改 CI 让自己“通过”）。

### 4.5 交付
- **验证报告**（核心差异化）：PR 描述自动附上：复现步骤、修改摘要、实际运行的测试及结果（从执行记录生成，不由模型自述）、自评置信度、已知风险。
- **写代码和审查分离**（Orbi、dsh）：修完后由独立的 reviewer agent 审一遍，审查意见和处理结果附在 PR 里；最多 3 轮。
- **诚实的草稿**（dsh）：没把握就开 draft PR，写明卡在哪；完全修不了就在 issue 里一句话说明原因，不硬交。
- **撞车让路**（dsh）：发现人已经提了同样修复的 PR，关掉自己的。

### 4.6 人机协作与通知
- **少打扰**（dsh）：接单确认一次（说清要改什么）、完成通知一次；中间进度只在控制台看。
- **结构化提问**：卡住时在原 issue 里问一个具体问题，人回复后自动继续（PR 评论回流，dsh 的 Subscription）。
- **飞书 / 企业微信通知**：只推“需要人看”的东西（待审 PR、需要决定的问题）。

### 4.7 可观测与运维
- **控制台**（OpenHands 的 Web UI）：工单列表按“需要人处理 / 进行中 / 已完成”排序；trace 回放（每步的思考、工具调用、diff）；成本与耗时看板。
- **持久化任务队列**（dsh Effects）：SQLite / Postgres 队列，重试、退避、重启恢复；429 / 额度错误的分类处理（你已经踩过的坑直接变成产品功能）。
- **observe 模式**（dsh）：新仓库先开“只记录不动手”，维护者看一周“它本来会怎么做”，满意了再开自动模式。

### 4.8 模型与成本
- **多模型路由**：便宜模型做审查和分诊，强模型做修复；失败时自动升级到强模型重试一次。可以做成实验：路由 vs 全强模型的解决率和成本。
- **Prompt 缓存友好**：稳定内容在前，变化内容在后（你的缓存命中已经 95%，写进文档当卖点）。
- **成本账单**：每个工单、每个仓库的 token 与人民币成本，月度汇总。

### 4.9 评测即产品功能（你的最大优势）
- **私有回归评测集**：从仓库 git 历史挖“改了源码 + 改了测试”的提交，回退源码改动、保留测试作为隐藏测试，自动生成题目（就是你 hard2 的生成思路，泛化到任意仓库）。
- **夜间回归**：每晚用固定题集跑一遍，prompt / 模型 / 工具改动导致的退化自动报警。
- **线上效果指标**：PR 被合并率、被要求修改的轮数、被关闭率、平均人工审查时间——这是产品真正的北极星指标，比 SWE-bench 分数更有说服力。

## 5. 推荐的 MVP 切口

如果只能做一个方向，建议 **v0.2 CI 修复机器人**：
- 触发明确（CI 失败）、验收明确（CI 变绿），评测天然自动化；
- 真实需求强：依赖升级导致的测试失败、lint / 类型检查失败、flaky test，是团队里最烦人的杂活；
- 复用 nanocoder 现有的沙箱、工具、提交守卫，新增的主要是 GitHub 集成和日志解析；
- 评测集好造：在开源仓库上找“CI 红 → 下一个提交修绿”的历史提交对。

v0.1 PR 审查可以作为顺手的第一个发布（几天就能做完），先让别人装上用起来。

## 6. 简历上怎么写（产品化版本）

> **nanocoder：自托管的仓库 AI 队友**（Python / Docker / GitHub App / SQLite）
> - 设计并实现事件驱动的后台 coding agent：GitHub 评论、标签、CI 失败统一转为工单，在 Docker 沙箱中复现、修复并交付带验证报告的 PR；已在 N 个仓库试用，PR 合并率 X%。
> - 实现持久化任务队列、错误分级重试、环境快照预热（冷启动从 X 分钟降到 Y 秒）、每任务成本护栏与 observe 灰度模式。
> - 构建从 git 历史自动生成私有回归评测集的工具与夜间回归流水线；SWE-bench Verified 50 题子集解决率 X%。

真实用户数据（哪怕只是你自己和同学的 3～5 个仓库）比任何跑分都有说服力。
