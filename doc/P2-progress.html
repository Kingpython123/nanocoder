路上踩过的坑（都是好的面试素材）

  • 基础设施故障被算成模型失败。“推理 high + E8”第一次只有 66.7%，比基线还低。查下来 12 次失败全是 429 限流。之后 runner 把 llm_error、harness_error 单独分类，比较前先看结束原因分布。
  • patch 丢了新建文件。agent 新增的模块没进 git diff，patch 引用了不存在的文件。改成用 git add -N 纳入。
  • 额度耗尽后白拉镜像。403 不会被重试，每题第一步就失败，却仍要拉 4GB 镜像。runner 现在遇到 403 就在当前批次结束后停下。
  • 测试空转通过。回放 MobileWorld 时缺 psycopg2，任务注册表为空，测试在合并前的代码上也通过。装好依赖确认有 183 个任务后才复现出问题。

简历说法

从零实现 Coding Agent（ReAct 循环、Docker 沙箱、可断点续跑的评测流水线），用官方 harness 在 SWE-bench Verified 按仓库分层抽样的 50 题子集上解决 40 题（80%，单次运行）。在自建的隐藏测试任务集上做消融，规格清单与推理叠加后解决率从 72% 提升到 97%（36 次运行）。用已合并的开源 PR 做回放：MobileWorld 的 issue 改写成只描述现象后，agent 仍给出与 PR 一致的修复。

被问到时要主动说明：跑分中途换过模型；PR 不是 nanocoder 写的；回放只跑了几个案例；97% 是自建任务集的结果，题目由自己设计。失败归因做完后，这段可以再加一句失败原因分布。

术语

F2P
Fail-to-pass，修复前失败、修复后应通过的测试，检查问题有没有修好。
P2P
Pass-to-pass，修复前后都应通过的测试，检查有没有改坏别的东西。
resolved
F2P 和 P2P 全部通过才算解决。
pass@1
所有运行的平均通过率。
pass^3
连续 3 次都通过的题目比例，衡量稳定性。
k
每题重复运行的次数。
E7 / E8
消融实验编号。E7 是开推理，E8 是规格清单 prompt（v2_spec）。
harness
SWE-bench 官方评测程序：在镜像里打 patch、跑测试、判定结果。
